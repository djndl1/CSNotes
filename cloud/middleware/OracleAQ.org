* History

- Core component of Oracle database since 8i.

- AQ Sharded Queues (12.2), rebranded as TxEventQ in 21c

* Concepts

- *agent* =AQA$_AGENT=: producer or consumer of a message
g + name, protocol, address

- *recipient*: an agent that receive a message

- *subscriber*

* Patterns

- point-to-point

- pub-sub supported via multi-consumer dequeuing.
  All messages enqueued in the queue are made available to be consumed by each of the queue subscribers.
  + each subscriber can specify a rule which represents  a specification for he messages that
    the subscriber wishes to receive.

- multicast: A message producer can submit a list of recipients (only by name) at the time a message is enqueued
  into a non-sharded queue. This allows for a unique set of recipients for each message
  in the queue. The recipient list associated with the message overrides the subscriber
  list associated with the queue, if there is one. The recipients need not be in the
  subscriber list.

Messages can be buffered (in-memory only) or persistent. In legacy AQ
buffered messages cannot be published without static registration. 
Buffered messages can not have actual LOB data (the field can be there but null). 
Buffered messages do not participate in external transaction (immediate visibility).
Also, array dequeue is not supported for buffered messaging for non-sharded queues. 
Buffered messages are gated to prevent the memory (streams pool) from message flooding: the sender
blocks on enqueuing and timeout with an error. Older messages are spilled to disk to free up memory
to prevent faster subscribers from getting bogged down by slower subscribers.

Array enqueue/dequeue and PL/SQL notification are only supported for sharded queues for buffered
messaging. Message retention (message kept in the queue table for some time) transaction grouping, message export/import are not supported for
buffered messaging.

- Asynchronous notification: the server calls back to the client by creating a new connection to a
 (specified or random) port of the client. A client may even register for the first notification
only or a time interval.

* Enqueue and Dequeue

- Array (batched) enqueuing and dequeuing are supported

- *correlation identifiers*: assigned to specific messages to retrieve at a later time

- priority can be assigned to messages but it is not the only sorting criteria. 
  A sort order is specified at table creation time: priority, enqueue time or commit time.
  A queue may not be a strict FIFO due to flexible ordering.

- *message grouping*: group messages in a transaction so that they are consumed by the same user.
  + useful for segmentation.
  + not supported by buffered messaging

- The sender can mark the messages with a custom identification.

- An expiration time may be assigned to a message.

- dequeuing is concurrency-safe: no messages are consumed by two receivers.

- dequeuing can be out-of-order
  + by correlation identifier (user defined)
  + by message identifier (system assigned)
  + specified by other conditions
  + default (in order): the first available message
  + navigating through the queue: =FIRST_MESSAGE=, =NEXT_MESSAGE=, =NEXT_TRANSACTION= (grouping).
    Non-zero wait time at the end of a queue moves the cursor back to the beginning. Using zero wait time 
    throws an exception.

- dequeuing modes:
  + browse (peek)
  + remove (receive)
  + remove with no data (deleted without retrieval)

- =DEQUEUE= a single queue or =LISTEN= (select) on multiple

- Dequeuing may fail and application is allowed to retry for a few times (specified at the queue level)

- Message states:
  + WAITING
  + READY: dequeuable
  + PROECSSED: all intended consumer have dequeued the message
  + EXPIRED: expired messages will be moved an exception queue.

** Propagation

Messages being passed form one queue to another (local or remote).

Propagation can be *dedicated* (immediate), *event-based* (delayed but at a certain time later) or *periodic*.
A schedule indicates the time frame during which messages can be propagated from
the source queue.

*** Use Cases

- Messages can be fanned out to a large number of recipients without requiring them all to dequeue
  messages from a single queue. 

- Combining multiple queues into a single queue.

- integrating messages across database servers.

- remote subscription (federated)

*** Two Modes

- Queue-to-dblink: propagation from a source queue to subscribers via a dblink

- Queue-to-queue: point-to-point

* Background Processes & Maintenance

** Queue Monitor Processes

- message state transition

- spilling and recovering of buffered messages

- moving messages to exception queues

** Job Queue Processes

Handle propagation and PL/SQL notifications.

* API

** PL/SQL

Full AQ administration capability.

Administrative and operational

- =DBMS_AQ=: operational interface 

- =DBMS_AQADM=: administrative interface

- RAW payload limited to 32K

** JMS Message Service using =oracle.jms=

Administrative and operational. Standard JMS interface support.

- Creating RAW message is not supported.

** C/OCI

Operational only. 4G Raw payload limit. Unsuitable for sharded queues.

** AQ XML Servlet — SOAP / IDAP

 accesses AQ over HTTP using SOAP and the AQ XML message format IDAP (Internet Data Access
 Presentation). A Web browser or any HTTP client can act as an AQ client, sending IDAP-conformant
 XML to the servlet, which interprets it, connects to the database and operates on user queues.
